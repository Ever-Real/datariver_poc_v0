# ADR-0088: Schema Quality dashboard and managed indicators

- Status: Accepted
- Date: 2026-07-31
- Owners: Product, Data Architecture, Application, Data Platform
- Refines: ADR-0077, ADR-0078, ADR-0081, ADR-0084

## Context

ADR-0081 reduced the ordinary Quality workspace to an asset inspector and reusable common Rules.
That simplified daily table work, but it removed the cross-schema view that a data owner needs to
answer three questions quickly:

1. how many tables are in each visible schema;
2. how accuracy, completeness and timeliness compare across those schemas; and
3. which tables and fields make an indicator risky.

These indicators cannot be inferred from names or generated by the browser. Accuracy is not a
claim that a value is true in the real world unless an accountable owner has encoded the applicable
domain constraint. Timeliness also cannot use an invented fixed number of days when the Profile
projection already carries a server-owned `stale_at` decision. A generated narrative must not be
shown as an LLM report until a Quality-specific governed inference route and evidence contract
exist.

The current deployment may also return
`FIELD_IDENTITY_MAPPING_UNAVAILABLE` to an administrator. That is a deployment-readiness result,
not a role error: ADR-0079 requires both a V2 server-owned field directory and the applicable V3/V4
Quality retention classes. Administrator authority does not substitute for either input.

## Decision

### Information architecture

The ordinary Quality page has three primary tabs:

1. `품질 대시보드`;
2. `자산별 품질 현황 및 이력`; and
3. `공통 룰셋 관리`.

The asset tab reuses the Catalog Search global-search component and its lazy
`platform -> database -> schema -> asset` Resource Tree. Component instance IDs are caller-scoped,
so rendering the same search control in the application header and Quality panel does not create
duplicate label, listbox or error IDs. The existing asset inspector remains the canonical view of
applied Rule Sets, recent Runs and score trend.

The common-Rule view keeps creation separate from deployment readiness. A permitted user may create
a non-executable template while mapping stays disabled. The view explains that an administrator
still needs the deployment-owned V2 field directory and current V3/V4 retention readiness, and it
shows the server reason code. It does not synthesize field identities from Catalog labels or bypass
the existing atomic mapping command.

### Dashboard read model

Add `GET /quality/dashboard`. It is a human-only, `quality.read` read model with the same 30-second
authorization lease, permission-bound `cache_scope`, forced-RLS lower bound and
authorization-pruned Catalog asset relation as other Quality reads. Profile evidence is added only
after the independent `quality.profile.read` decision. The response is bounded to 500 schema rows
and 50 detailed risks per schema indicator; truncation is explicit.

The top-level values are:

- visible schema and table counts;
- visible active Rule Set and common-Rule-template counts; and
- table coverage, where a visible table contributes once when it has at least one ACTIVE Rule Set.

The response contains three versioned platform-managed indicator definitions under
`QUALITY_MANAGED_INDICATORS_V1`. They are read-only definitions, not executable templates and not
additional canonical Rule Sets:

- `ACCURACY` targets fields with active `RANGE` or future safety-approved `REGEX` Rules. Its score
  pools `(evaluated_count - unexpected_count)` over evaluated values from the latest `SUCCEEDED`
  Run for each active Rule Set's current ACTIVE Version.
- `COMPLETENESS` targets fields with active `NOT_NULL` Rules. Its score pools
  `(evaluated_count - missing_count)` over the same latest-success evidence.
- `TIMELINESS` targets visible tables. Its score is the number whose latest COMPLETE
  FULL/PARTITION Profile remains before its stored `stale_at`, divided by all visible tables in the
  schema. Missing Profile evidence is advisory risk and stale Profile evidence is blocking risk.

Accuracy and completeness target coverage counts distinct `(asset, field identifier)` targets and
the subset with a current expectation result. Their scores are value-weighted; they do not replace
ADR-0084's Rule-weighted asset badge. Timeliness is Profile freshness, not a claim about an
unobserved source update timestamp. Zero evidence returns `null`/`UNKNOWN`, never a fabricated
zero score.

The analysis dialog switches among the three indicators without leaving the selected schema. It
shows target/count coverage, a gauge backed by the numeric response, the server calculation
definition and a bounded risk table. Expanding a risk row shows only sanitized counts and details;
it never returns failed values or rows.

### Report boundary

The initial report state is `FACTS_ONLY` with
`QUALITY_LLM_REPORT_ROUTE_UNAVAILABLE`. The server composes a bounded statement exclusively from
the returned aggregate. The UI labels it as a server fact summary and explicitly states why it is
not an LLM-generated report. `LLM_GENERATED` may be used only after a separate accepted
Quality-specific inference route binds the exact authorized evidence, provider/model policy,
retention and citation/provenance contract.

### Persistence

This decision adds no table, column, migration or executable default Rule. It is an
authorization-pruned read-model/API/UI change over existing Catalog Profile and Quality evidence.
The current required database revision remains unchanged.

## Consequences

- Users regain a compact schema comparison without restoring the old control-plane, Issue or
  maker-checker navigation.
- Platform defaults define consistent indicator semantics while accountable typed Rules still
  determine which fields are targets.
- Catalog hierarchy and search behavior stay consistent between Search and Quality.
- Administrators receive an actionable readiness explanation without weakening deployment-owned
  identity or retention gates.
- The Quality-specific LLM narrative, target Profile/source execution, representative database
  plan and manual browser accessibility remain explicit external gates.
